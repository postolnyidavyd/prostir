# Простір - бронювання переговорних

Внутрішній застосунок, у якому співробітник дивиться тижневий розклад переговорної,
бачить зайняті слоти і бронює вільний час. Своє бронювання можна скасувати, чуже - ні.

Монорепо з трьох частин: `web/` (React + Vite + TypeScript + styled-components),
`api/` (Express + TypeScript + Prisma) і `docker-compose.yml`, що піднімає обидві разом
із PostgreSQL.

## Швидкий старт

Потрібен лише Docker. З кореня репозиторію:

```bash
cp .env.example .env
docker compose up
```

Одна команда збирає обидва образи, піднімає Postgres, застосовує міграції, засіває
демо-дані й запускає застосунок. Коли контейнери стартували, відкрий:

- веб - http://localhost:5173
- API - http://localhost:4000

`.env.example` уже містить робочі локальні дефолти, тому редагувати нічого не треба.
Порти (`WEB_PORT`, `API_PORT`, `POSTGRES_PORT`) і секрети лежать там, якщо захочеш змінити.

## Локальна розробка

Якщо зручніше запускати частини окремо (з hot-reload), підніми лише базу через Docker,
а `api` і `web` - локально. Потрібен Node 22+.

```bash
docker compose up -d postgres        # тільки база

cd api
npm install
npx prisma migrate dev               # застосувати міграції
npm run seed                         # демо-дані
npm run dev                          # http://localhost:4000

cd ../web
npm install
npm run dev                          # http://localhost:5173
```

## Сіди

У Docker сіди застосовуються самі при старті `api`. Запустити повторно вручну:

```bash
docker compose exec api npm run seed:dist      # у контейнері
npm run seed                                   # локально, з теки api/
```

Сіди ідемпотентні. Кімнати й користувачі оновлюються за унікальним ключем, а демо-бронювання
наповнюють лише порожню таблицю, тож повторний запуск не плодить дублів на нових датах.
Створюється 5 переговорних, троє тестових користувачів і кілька бронювань на найближчі дні.

## Тести

З теки `api/`:

```bash
npm test          # юніт-тести логіки перетинів і часу, БД не потрібна
npm run test:db   # інтеграційні тести API поверх реальної бази
```

Юніт-тести покривають межові випадки перетину інтервалів: впритул, часткове перекриття,
повний збіг, сусідні дні. Для `test:db` має бути піднята база (`docker compose up -d postgres`),
адресу вона бере з `DATABASE_URL`.

## Як влаштована перевірка перетинів

Неперетин гарантує сама база, а не код застосунку. У таблиці бронювань стоїть
EXCLUDE-констрейнт на розширенні `btree_gist`: він забороняє два активні бронювання
однієї кімнати, чиї часові діапазони перетинаються. Діапазон береться як `tstzrange`
з межами `[)` - початок включно, кінець виключно. Саме через ці межі бронювання впритул
не конфліктують: для слотів 10:00-11:00 і 11:00-12:00 спільна точка 11:00 належить лише
першому діапазону, тож перетину немає. Константа часткова (`WHERE canceled_at IS NULL`),
тому скасоване бронювання звільняє слот і не заважає забронювати його знову. Коли двоє
одночасно тиснуть «забронювати» на той самий час, обидва запити доходять до бази, але
констрейнт пропускає рівно один; помилку другого сервіс ловить і віддає людське
повідомлення «слот щойно зайняли» (409). Тобто останнє слово завжди за базою, а не за
перевіркою в пам'яті, яку можна обійти паралельним запитом.

## Як зберігається час

У базі час завжди в UTC (`timestamptz`), без прив'язки до пояса. В інтерфейсі кожен слот
показується вже переведеним у пояс браузера користувача, тому людина з Берліна бачить ту
саму сітку зі зсувом на годину. Робочі години кімнат (09:00-19:00) і всі правила створення
живуть у київському часі й перевіряються на сервері через `date-fns-tz`, незалежно від того,
де сидить користувач. На сервер бронювання приходить парою ISO-міток у UTC, а він валідує:
час кратний 30 хвилинам, тривалість від 30 хвилин до 4 годин, слот у майбутньому і в межах
робочих годин за Києвом. Якщо пояс браузера відрізняється від київського, над сіткою
з'являється підпис із поясненням, щоб зсув не збивав з пантелику.

## Формат помилок API

Будь-яка помилка повертається JSON однієї форми, ніколи HTML. Поле `message` є завжди,
воно українською і його можна показати користувачу як є. Поле `errors` присутнє лише
у валідації (400): ключ поля вказує на масив повідомлень, вкладені поля йдуть через крапку
(`room.id`), а якщо проблема в самій частині запиту - ключем стає `body` / `query` / `params`.

```json
{ "message": "Некоректні дані запиту", "errors": { "title": ["Назва не може бути порожньою"] } }
```

| Код | Коли |
|-----|------|
| `400` | не пройшла валідація або тіло не є валідним JSON |
| `401` | немає access-токена, він протермінований або підроблений |
| `403` | токен валідний, але дія чужа (скасування не свого бронювання) |
| `404` | немає такого маршруту або ресурсу |
| `409` | конфлікт стану: слот зайнятий, email уже зареєстрований |
| `500` | усе інше; `message` загальний, деталі лише в лог сервера |
