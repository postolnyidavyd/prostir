# Простір - бронювання переговорних

Застосунок, у якому співробітник дивиться тижневий розклад переговорних,
бачить зайняті слоти, бронює вільний час.

Монорепо з трьох частин:
- `web/` (React + Vite + TypeScript + styled-components),
- `api/` (Express + TypeScript + Prisma)
- `docker-compose.yml`, що піднімає обидві разом із PostgreSQL.
## Що вміє

- **Вхід і реєстрація** - email + пароль; сесія переживає перезавантаження (JWT access у пам'яті + refresh у httpOnly-cookie)
- **Кімнати** - 5 переговорних (назва, поверх, місткість). Робочі години 09:00–19:00 за Києвом, однакові для всіх днів - субота й неділя бронюються нарівні з буднями (ТЗ не вимагав вихідних; виключити їх - точкова зміна в одній серверній перевірці)
- **Тижневий розклад кімнати** - сітка "дні x час" по 30 хв; зайняті слоти видно всім (назва бронювання + хто забронював), тижні гортаються вперед/назад. Свої бронювання виділені, поточний день і час підсвічені.
- **Часовий пояс** - увесь час показується в поясі браузера; якщо він не київський, над сіткою підпис із офісним поясом. Робочі години й правила перевіряються за Києвом
- **Створення бронювання** - кімната, дата, час, назва. Вибір часу можливий драгом по сітці: тягнеш від початку до кінця, виділення кратне 30 хв і впирається в найближчу чужу броню/4 години. Валідація на сервері: час кратний 30 хв, тривалість 30 хв – 4 год, лише в майбутньому й у робочих годинах, без перетину з наявними.
- **Скасування** - лише своє; чуже не скасувати ні через інтерфейс, ні прямим запитом до API
- **Мої бронювання** - майбутні й минулі з пагінацією; клік по рядку веде в сітку на відповідний тиждень.
- **Профіль** - зміна імені/email і пароля, вихід з усіх сесій
## Швидкий старт

Потрібен лише Docker. З кореня репозиторію:

```bash
cp .env.example .env
docker compose up
```

Одна команда збирає обидва образи, піднімає Postgres, застосовує міграції, застосовує сіди й запускає застосунок.
Коли контейнери стартували:
- Фронт - http://localhost:5173
- Бек - http://localhost:4000

`.env.example` уже містить робочі локальні дефолти.

## Локальна розробка

Для локальної розробки запускати командами (потрібна Node 22+):
```bash
docker compose up -d postgres        # тільки база даних

cd api
npm install
npx prisma migrate dev               # застосувати міграції
npm run seed                         # демо дані
npm run dev                          # http://localhost:4000

cd ../web
npm install
npm run dev                          # http://localhost:5173
```

## Сіди

У Docker-Compose сіди застосовуються самі при старті `api`. Запустити повторно вручну:

```bash
# у контейнері
docker compose exec api npm run seed:dist

# локально, з теки api/
npm run seed
```

Сіди ідемпотентні: кімнати й користувачі оновлюються за унікальним ключем, а демо-бронювання наповнюють лише порожню таблицю - повторний запуск не плодить дублів.

Створюється 5 переговорних, троє тестових користувачів і кілька бронювань.

Дати броней рахуються від понеділка поточного тижня -  але лише при першому сіді: повторний запуск на новий тиждень їх не перенесе (щоб оновити демо дати, потрібен чистий volume - `docker compose down -v`).

## Що реалізовано
### Бонуси з ТЗ

- **Docker Compose** -  одна команда піднімає все: postgres  api, web (nginx). Health-check на базі, api стартує лише коли postgres `healthy`.
- **Захист від гонки** - неперетин гарантує сама БД: два одночасні "забронювати" на той самий слот доходять до бази, але лишається рівно одне, другому летить 409. Механізм у розділі [Як влаштована перевірка перетинів](#як-влаштована-перевірка-перетинів)
- **Фільтр кімнат за місткістю** - показує кімнати з кількістю місць **не менші** за задану.
- **Мобільна адаптація** - сайдбар їде в лівий дровер, тижнева сітка на телефоні показує один активний день із перемикачем лише одного дня замість тижня, а драг вибір замінено на тап-створення (драг на тачі конфліктує зі скролом)
- **Сповіщення про кінець** - RTK Query опитує ендпоінт, клієнт ставить `setTimeout` на момент `endsAt − N` і показує тост; рівно раз тримає `localStorage` (id останнього показаного, переживає релоуд); не приходить, якщо будь-яке з двох бронювань скасоване.
- **Підтвердження email (dev)** - без SMTP: одноразовий токен (у БД лише sha256 хеш), посилання в лозі сервера. До підтвердження створення бронювань блокує middleware на сервері; На фронті показується плажка про непідтверджений email та має сторінку для підтверження паролю; сідові юзери вже підтверджені
- **Повторювані бронювання** -  щотижнева серія зі спільним `seriesId`. Якщо частина тижнів зайнята - показуємо які й питаємо підтвердження, тоді бронюємо доступні (best-effort), інакше все-або-нічого в транзакції. Крок тижня рахується у часі Києва, тож зустріч не з'їжджає через переходи на літній/зимовий час. Скасувати можна одне повторення або всю серію
- **Тести** - окремо юніт на чисті функції (перетини, час) і інтеграційні на API поверх реальної БД. Детально - у розділі [Тести](#тести)
### Понад ТЗ
- **Живе оновлення розкладу (WebSocket)** - власний `ws`-сервер, канал на кімнату; сервіс після create/cancel шле сигнал, клієнт інвалідовує теги кешування RTK Query і перезапитує REST. Джерело істини лишається за БД - сокет лише про свіжість, застосунок працює й без нього.
- **Лендінг** - окрема сторінка для неавторизованих (`/welcome`), як і всі інші сторінки зверстаний з Figma
- **Розширений фільтр кімнат** - крім місткості: за поверхом, за вікном часу (`from/to`) з позначкою вільна/зайнята на кожній кімнаті й перемикачем "тільки вільні" (тільки вільний у вказаний час `from/to` )
- **Безпека сесій** - refresh у httpOnly-cookie з ротацією на кожному оновленні access токена; повторне використання старого токена трактується як крадіжка й розлоговує всі сесії. Зміна пароля теж розлоговує всі пристрої.
- **Стан у URL** - кімната/тиждень/день у query (`?room=&week=&day=`), тож посилання на конкретний розклад шаряться й переживають релоуд


## Як влаштована перевірка перетинів
Неперетин гарантує сама база, не код застосунку. На таблиці `bookings` висить EXCLUDE-констрейнт (`btree_gist`): для однієї кімнати два записи не можуть мати діапазони часу, що перетинаються.
Діапазон береться як `tstzrange(starts_at, ends_at, '[)')` - межа напіввідкрита, тож сусідні слоти 10:00 – 11:00 і 11:00 – 12:00 **не** конфлікт. Констрейнт частковий - `WHERE canceled_at IS NULL` - тому скасовані бронювання (soft delete) звільняють слот і нікому не заважають.

Через це захист від гонки безкоштовний: перевірка "чи вільно" перед вставкою від гонки не
рятує (між `SELECT` і `INSERT` слот міг зайняти хтось інший), тож її як гарантії немає взагалі.
Два одночасні "забронювати" на той самий слот обидва доходять до бази - лишається рівно одне, другий ловить помилку констрейнта, парситься з обгорнутою prisma помилку дб, яку сервіс перетворює на 409 "слот щойно зайняли"

Функція `intervalsOverlap` у коді все ж є, але вживається **тільки** в юніт-тестах (щоб `npm test`
проходив без піднятої БД); у рантаймі рішення завжди за констрейнтом, а тести звіряють, що функція й база дають однаковий результат на тих самих кейсах(було перевірено)

## Як зберігається час

У базі час лежить у UTC (`TIMESTAMPTZ`) — момент без прив'язки до пояса. Клієнт шле початок і кінець в ISO з `Z`, показує все у поясі браузера. Якщо браузер не в київському поясі, над сіткою показуєть жовтий бейдж попередження з часовим поясом користувача і попередженням про різні часові пояси, щоб не було плутанини, о котрій годині насправді слот.

Робочі години й усі доменні правила рахуються **за Києвом** незалежно від пояса сервера чи
браузера: 09:00 - 19:00, крок 30 хв, тривалість 30 хв - 4 год.
Це ж стосується повторюваних серій - тижневий крок додається у київському часі, тож при переході на літній/зимовий час зустріч лишається о тій самій годині, а не з'їжджає на годину
## Тести

Два набори, розведені навмисно:

- **Юніт** (`npm test`) - чисті функції без БД і без мережі: перетини (`overlaps`), час і робочі
  години (`time`), розбір імен (`names`), токени (`tokens`). Кейси перетинів покривають межі - впритул, часткове перекриття, повний збіг, сусідні дні. Швидко, нічого піднімати не треба

- **Інтеграційні** (`npm run test:db`, потрібен піднятий Postgres) - поверх реальної бази й
  реального констрейнта: auth, bookings, `no-overlap` (гонка на один слот), нагадування про
  кінець, realtime (вебсокет), серії. Файли ділять рядки в одній базі, тож паралелізм вимкнено (за умовчуванням vitest всі тестові файли летять паралельно, із-за чого різні тести б наступали один одному на ноги при вставлені своїх рядків в бд)

## Помилки API

Помилки не розкидані по контролерах - сервіси й middleware кидають типізовані винятки
(`AppError` з кодом і українським `message`, плюс `ValidationError` і `SeriesConflictError`), а один error-handler у кінці ланцюжка їх ловить і серіалізує в єдину JSON-форму.
Zod-валідація дає `ValidationError` з мапою полів (`errors`), биті JSON-тіла - 400, усе неочікуване - загальний 500 (деталі лише в лог, не клієнту). Тож клієнт завжди отримує однаковий контракт: `message` українською, який можна показати як є, і `errors` тільки там, де є що показати по полях.

```json
{ "message": "Некоректні дані запиту", "errors": { "title": ["Назва не може бути порожньою"] } }
```
